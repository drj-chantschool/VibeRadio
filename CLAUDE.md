# VibeRadio

Android audio player that behaves like a radio: a few generated channels, one knob, no skip/seek/track list on the song side. Podcasts are a separate, hand-curated pipeline with their own page. See README.md for the concept and the issues for planned features.

## Specs

The product specs live in `docs/` and are the source of truth for behaviour. Read the relevant one before changing a feature, and update it in the same PR when a decision changes.

- `docs/features.md`: product principle, channels, podcast page and scheduling, audio chain and defaults, song shuffle and resume, diagnostics export
- `docs/learning.md`: song learning (feature vectors, channel-fit and preference models, seasonal weighting, thumbs, coverage rule)
- `docs/similarity-plan.md`: phased plan for audio-similarity channel placement (Phase 0 logging through a learned metric)
- `docs/audio-features.md`: the per-song audio feature vector (blocks, extractors, model manifests, similarity space) and the library survey
- `docs/look-and-feel.md`: visual direction

## Build

Requires JDK 17+ (CI uses 21) and an Android SDK (`ANDROID_HOME` or `local.properties`).

```sh
./gradlew assembleDebug          # debug APK -> app/build/outputs/apk/debug/
./gradlew testDebugUnitTest      # JVM unit tests
./gradlew installDebug           # install on a connected device
```

CI (`.github/workflows/ci.yml`, job `check`, required by the "Protect main" ruleset) runs actionlint, then `assembleDebug assembleRelease lint testDebugUnitTest` on every PR and push to `main`.

`tools/similarity-lab` is a separate Python package (`vrlab`, numpy; onnxruntime and ffmpeg for `extract`): the PC side of the similarity plan's Phase 2. It ports `SimilaritySpace`, `PropagatedChannelFit`, `ModelSpec`/`MelSpectrogram`, `ExcerptPlan`/`Resampler`, `ContentHash` and the feature block files, so **a change to any of those in the app needs the same change there**. Tests: `python -m unittest discover -s tests -t .` from that folder (CI job `similarity-lab`, not required).

**Cloud sessions (Claude Code on the web or the mobile app) don't build: CI is the build.** Their containers have no Android SDK (no `ANDROID_HOME`, no `local.properties`), so don't run `./gradlew`, and don't try to download or install an SDK, Gradle distribution or JDK to make it work. Review the diff carefully instead, open the PR, and let the `check` job build, lint and test it. If `check` fails, read the job log through the GitHub tools, fix it on the same branch and push again. Only build locally when the SDK is already there.

The app version comes from the release tag, never from source: `-Pviberadio.versionName=1.2.3` (or `1.2.3-alpha|beta|rc.N`) sets `versionName`, and `versionCodeOf` in `app/build.gradle.kts` derives a `versionCode` that sorts the same way. Without the property the build is `0.0.0-dev`, versionCode 1.

Release signing reads `VIBERADIO_KEYSTORE_PATH`, `VIBERADIO_KEYSTORE_PASSWORD`, `VIBERADIO_KEY_ALIAS` and `VIBERADIO_KEY_PASSWORD` from the environment; without them `assembleRelease` produces an unsigned APK. Debug builds use the `app.viberadio.debug` ID and the label "VibeRadio dev", so they install next to the release app.

## Releases

Distribution is GitHub Releases, installed and updated on-device with Obtainium. `.github/workflows/release.yml` validates the version, runs unit tests, builds a signed release APK with that version, verifies the signature and publishes `viberadio-<version>.apk` (plus a `.sha256`) as a GitHub Release. Versions with `-alpha.N`, `-beta.N` or `-rc.N` publish as pre-releases.

**Every PR ships itself.** Opening a PR is the whole job: `auto-merge.yml` arms auto-merge, the PR merges when `check` passes, and `.github/workflows/auto-release.yml` then releases when CI passes on `main`. It bumps the patch of the newest stable tag and dispatches Release for the commit CI passed (skipped if `main` has moved on; the newer commit's CI run releases it). Sessions never start a release for a merged PR and don't wait to be asked. The chain needs CI to run on `main` after the merge, and pushes made with the Actions token start no workflows, so if a merge produced no CI run, no release follows: fix the token in `auto-merge.yml` rather than releasing by hand. For a pre-release or a minor/major bump, start one by hand:

Start a release by hand either way:

- **Run workflow** (works from a phone browser): Actions → Release → Run workflow on `main`, version e.g. `0.2.0` or `0.2.0-beta.1`. The workflow creates the `v` tag on the `main` commit it built. This is the route for Claude sessions, which cannot push tags.
- **Push a tag:** `git tag v0.2.0 && git push origin v0.2.0`.

Repo secrets the workflow needs: `VIBERADIO_KEYSTORE_BASE64` (the `.jks`, base64-encoded), `VIBERADIO_KEYSTORE_PASSWORD`, `VIBERADIO_KEY_ALIAS`, `VIBERADIO_KEY_PASSWORD`. The keystore is permanent: every update must be signed with it, so it lives offline as well as in secrets and never in the repo.

## Dependencies

Dependency versions live only in `gradle/libs.versions.toml`. AGP 9 compiles Kotlin itself (built-in Kotlin): do **not** apply `org.jetbrains.kotlin.android`. The `kotlin` version in the catalog pins the Kotlin compiler via the Compose compiler plugin.

minSdk is 26. Nothing in #1–#6 needs higher: Media3 `AudioProcessor`s, `LoudnessEnhancer` and on-device classification all run on 26. API 26 also guarantees notification channels and adaptive icons. The one API split is genre lookup (see below).

Tuning flow: knob release → `RadioViewModel.tune` → `controller.setMediaItem(ChannelRequest.mediaItem(id))` → `RadioSessionCallback.onSetMediaItems` → `StreamPlanner.plan` then `LiveRadio.tuneIn` (song channel) or `PodcastLibrary.queue` (podcast-only channel) → queue. Each queued item carries the channel ID in `MediaMetadata.extras` (`ChannelRequest.EXTRA_CHANNEL_ID`) so the UI follows service-side channel changes. Song items also carry their content URI (`ChannelRequest.EXTRA_TRACK_URI`), which is how the song page knows what a thumbs press refers to; episodes don't, so the thumbs hide for them. Thumbs state is per play (`PlayThumbs`): a press stays lit only until the next media item transition or the end of playback, and is never read back from the log, so every play (even of the same song) starts neutral. Until then the lit thumb pressed again cancels and the other thumb switches (`PlayThumbs.press`); `RadioViewModel` logs only the thumb lit when the play ends (or when the view model is cleared), so a cancelled or replaced press never reaches the log.

## Conventions

- **The product rule is the spec.** You still have control, but you shouldn't need it, and the app doesn't encourage using it in an unhealthy way; defaults should be right the first time.
  - **Song side (strict):** one knob. No skip, seek, track list, or second control. If a feature seems to need one, raise it instead of adding it. The thumbs (#13) are feedback, not control: they never skip or change the queue. The play glyph in the dial's centre only starts or resumes playback and disappears while playing; there is no pause button.

## Workflow

- **Work it through without stopping to ask.** Ask the user something only when the request is vague, or inconsistent with the specs in `docs/` or the current state of the code. Otherwise make the reasonable call and say what you decided in the PR description.
- **When development is done, open the PR.** Don't ask whether to open one; skip this if one is already open for the branch. Branch from `main`, one logical change per PR, referencing the issue (`#n`). Update the relevant `docs/` spec in the same PR when behaviour changes.
- **Auto-merge arms itself.** `.github/workflows/auto-merge.yml` runs `gh pr merge --auto --merge` when a PR is opened, reopened or marked ready, so it merges itself once the `check` job passes. Nothing to do per PR; if a PR sits unmerged after CI passes, check that workflow's run (repo needs "Allow auto-merge" on).
- If CI fails, fix it on the same branch; auto-merge stays armed.
