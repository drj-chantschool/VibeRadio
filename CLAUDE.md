# VibeRadio

Android audio player that behaves like a radio: a few generated channels, one knob, no skip/seek/track list on the song side. Podcasts are a separate, hand-curated pipeline with their own page. See README.md for the concept and the issues for planned features.

## Specs

The product specs live in `docs/` and are the source of truth for behaviour. Read the relevant one before changing a feature, and update it in the same PR when a decision changes.

- `docs/features.md`: product principle, channels, podcast page and scheduling, audio chain and defaults, song shuffle and resume, diagnostics export
- `docs/learning.md`: song learning (feature vectors, channel-fit and preference models, seasonal weighting, thumbs, coverage rule)
- `docs/similarity-plan.md`: phased plan for audio-similarity channel placement (Phase 0 logging through a learned metric)
- `docs/look-and-feel.md`: visual direction

## Build

Requires JDK 17+ (CI uses 21) and an Android SDK (`ANDROID_HOME` or `local.properties`).

```sh
./gradlew assembleDebug          # debug APK -> app/build/outputs/apk/debug/
./gradlew testDebugUnitTest      # JVM unit tests
./gradlew installDebug           # install on a connected device
```

CI (`.github/workflows/ci.yml`, job `check`, required by the "Protect main" ruleset) runs actionlint, then `assembleDebug assembleRelease lint testDebugUnitTest` on every PR and push to `main`.

The app version comes from the release tag, never from source: `-Pviberadio.versionName=1.2.3` (or `1.2.3-alpha|beta|rc.N`) sets `versionName`, and `versionCodeOf` in `app/build.gradle.kts` derives a `versionCode` that sorts the same way. Without the property the build is `0.0.0-dev`, versionCode 1.

Release signing reads `VIBERADIO_KEYSTORE_PATH`, `VIBERADIO_KEYSTORE_PASSWORD`, `VIBERADIO_KEY_ALIAS` and `VIBERADIO_KEY_PASSWORD` from the environment; without them `assembleRelease` produces an unsigned APK. Debug builds use the `app.viberadio.debug` ID and the label "VibeRadio dev", so they install next to the release app.

## Releases

Distribution is GitHub Releases, installed and updated on-device with Obtainium. `.github/workflows/release.yml` validates the version, runs unit tests, builds a signed release APK with that version, verifies the signature and publishes `viberadio-<version>.apk` (plus a `.sha256`) as a GitHub Release. Versions with `-alpha.N`, `-beta.N` or `-rc.N` publish as pre-releases.

Start a release either way:

- **Run workflow** (works from a phone browser): Actions → Release → Run workflow on `main`, version e.g. `0.2.0` or `0.2.0-beta.1`. The workflow creates the `v` tag on the `main` commit it built. This is the route for Claude sessions, which cannot push tags.
- **Push a tag:** `git tag v0.2.0 && git push origin v0.2.0`.

Repo secrets the workflow needs: `VIBERADIO_KEYSTORE_BASE64` (the `.jks`, base64-encoded), `VIBERADIO_KEYSTORE_PASSWORD`, `VIBERADIO_KEY_ALIAS`, `VIBERADIO_KEY_PASSWORD`. The keystore is permanent: every update must be signed with it, so it lives offline as well as in secrets and never in the repo.

## Dependencies

Dependency versions live only in `gradle/libs.versions.toml`. AGP 9 compiles Kotlin itself (built-in Kotlin): do **not** apply `org.jetbrains.kotlin.android`. The `kotlin` version in the catalog pins the Kotlin compiler via the Compose compiler plugin.

minSdk is 26. Nothing in #1–#6 needs higher: Media3 `AudioProcessor`s, `LoudnessEnhancer` and on-device classification all run on 26. API 26 also guarantees notification channels and adaptive icons. The one API split is genre lookup (see below).

## Architecture

Single `:app` module, package `app.viberadio`. Manual DI in `AppContainer` (one instance on `VibeRadioApp`), shared by the UI and the playback service (same process).

| Package | Role | Extension points |
|---|---|---|
| `library` | `MediaStoreLibraryScanner` → `List<Track>`. Genre from `GENRE` column on API 30+, from the `Genres`/`Members` tables on 26–29. `ContentKind` from MediaStore podcast/audiobook flags. MIDI (`MidiFiles`: MIME type or .mid/.midi/.kar/.rmi) is skipped, never a song. `Track.folder` is the folder relative to its volume (`LibraryFolderPaths`: RELATIVE_PATH on 29+, the file path below). Library folders (Settings → Audio): `FolderExclusions` (pure) holds left-out subtrees plus files-only entries (from putting back a subfolder of a left-out folder); `FolderTree` (pure) builds the tree of folders holding audio (lone chains folded) and each row's in/partly/out state; `LibraryFolderSettings` holds it as a `StateFlow`, persisted by `PrefsLibraryFolderStore`. `ChannelRepository` keeps the raw scan (`scanned`, what the tree shows), applies its `filter` hook (the exclusions, awaited on load) before the generator, and `regenerate()`s from the last scan when they change. | #6: refine `ContentKind` by analysing audio |
| `channels` | `ChannelGenerator` (pure) groups tracks by normalised genre into ≤`maxChannels` channels (catch-all included), or a single "All", then appends "All songs" (music only, ≤20 min, never podcasts). With `slotIds` the generated channels take those IDs in order (the app uses the five mood slots, see `dial`). `ChannelRepository` runs its `place` hook (`Learner.place`) over the result and holds it as a `StateFlow`; `replace()` re-runs `place` on the last scan without rescanning. | #3: replace `ChannelTypeResolver.Untyped` and route by `ContentKind` |
| `playback` | `PlaybackService` (`MediaSessionService`) owns two ExoPlayers + `MediaSession`: the session player (music, podcast-only channels, music podcasts) and the overlay player (podcasts over music on song channels; no audio focus, follows the session player's play/pause), one per stream, each with its own EQ; the system mixes them. Shows assigned to a song channel (#2) start per `PodcastSchedule` (pure: one episode at a time; tuning in fresh is a boundary, joining part-way isn't). The gap after an episode is a swappable `PodcastGapRule` (pure, each with its own `GapParam`s): `TracksByLength` (default: after one over 15 min one extra full track before the next, over 30 min three) or `MusicRatio` (ratio × back-to-back podcast time of music, capped at a max gap, default 10 min, starting at a track boundary within ±tolerance, else part-way through the song; under the floor, no gap). Chosen in Settings → Podcasts (the gap rule shows only in developer mode), held by `PodcastGapSettingsRepository`, persisted by `PrefsPodcastGapStore`. Schedule times are on `OnAirClock` (runs while the session player plays); `RadioSessionCallback` checks every 500 ms while playing for a part-way start. Music podcasts always wait for a boundary. A music podcast (`Podcast.pauseMusic`) takes the next song's place in the session queue and plays by itself, then the music resumes; any other show plays on `PodcastOverlay` over the music. `RadioSessionCallback` expands a channel request into a queue and strips skip/seek/shuffle/repeat commands from **every** controller (notification, headset, our UI). For podcast-only channels it queues `PodcastLibrary.queue`, starts at the saved position, marks episodes played on finish, saves positions every 15 s and on retune, keeps the queued tail in step with the podcast page, sets the player to the current episode's show speed (pitch preserved; 1× for songs; controllers still can't change speed), and falls back to `Dial.fallback` when empty. Song channels use live-radio resume (#29, `LiveRadio`, pure): each channel remembers its last song (hash, duration, wall-clock start); tuning in while `now < start + duration` queues that song first at `now − start` with a 1.5 s fade-in (player volume), otherwise shuffles. Clock gone backward, file gone or song off the channel → shuffle. Podcasts never use it. | `StreamPlanner` for #2 (mixing) and #4 (fallback via `onExhausted`, called at track boundaries). `StreamPlanner.next` picks one song at a time; `RadioSessionCallback` keeps the current song plus one queued (`LOOKAHEAD`) and tops up at each song start, so learning changes apply from the next pick. Today `WeightedRandomStreamPlanner`: every pick is an independent weighted draw (no passes), weight = `p × (p × age)^1.5`, `p` = `Learner.preferenceWeight` (floor 0.1), `age` = time since last heard on the `ListeningClock` in channel cycles (cycle = the channel's total running time), capped at 20 cycles; never heard = 1 cycle. Just played → 0, so no back-to-back repeats; play frequency ≈ proportional to `p`; the exponent only sets how random the spacing is |
| `playback.audio` | `ProcessingRenderersFactory` installs `AudioProcessorProvider`'s chain for an `AudioStream` (MUSIC or PODCAST) into `DefaultAudioSink`. Each chain is `StreamGainProcessor` then `StreamEqProcessor` (both 16-bit/float PCM). **Leveling (#1):** one fixed gain per song or episode, never compression. `LoudnessMeter` (pure) measures BS.1770 integrated loudness (K-weighting, 400 ms blocks, −70 LUFS absolute and −10 LU relative gates) and sample peak; `TrackLevel.gainDb` = target − measured, cuts in full, boosts only up to a −1 dBFS peak. `LoudnessAnalyzer` (MediaExtractor + MediaCodec, background priority) decodes the whole file once; `Leveling` (pure) runs one measuring worker, current item first, and keeps results in `levels.tsv` (`FileLevelStore`) keyed `song:<content hash>` or `episode:<id>` (downloaded episodes only; streamed ones play at 0 dB). `LevelingWatcher` requests everything queued on both players; `AppContainer` also requests every downloaded episode. `StreamGainProcessor` learns which item its PCM belongs to from the sink's `StreamMetadata` (period UID → window → media ID) on the flush at each item boundary, so the gain changes sample-accurately at the boundary, with no ramp (`StreamGain`, pure). A level not known at an item's start is ramped in if it arrives within 15 s, otherwise used from the next play. **Mixing factor (#2):** while a podcast plays over music (`MixState.podcastOverMusic`) the music drops by `mixingFactorDb`, ramped. **EQ:** `StreamEq` (pure, RBJ biquads): with a podcast over music, the podcast gets a band pass and the music a wider partial notch (peaking cut), both centred geometrically; otherwise flat. The blend ramps, never snaps. Figures and ramp time are `AudioSettings` (defaults: target −18 LUFS, mixing factor −10 dB, 1–4 kHz, 700 Hz–5.7 kHz at −9 dB, 1.5 s), held by `AudioSettingsRepository`, persisted by `PrefsAudioSettingsStore`, edited in Settings → Audio. | #5 voice emphasis: add an `AudioProcessor` between gain and EQ; #6 music suppression on the PODCAST chain |
| `podcasts` | Independent of the song pipeline (#17): never imports `library` or `channels`. `RssParser` (JDK DOM) → `Feed`. `PodcastLibrary` (pure, immutable) holds shows, their hand-assigned channel IDs (#18, any named channel, song channels included), "Pause music" (`pauseMusic`, default off) and playback speed (`PodcastSpeeds` ladder, 0.8–2×, default 1×), and the global played set and resume positions (#19); `queue(channelId)` = started episode first, then oldest unplayed. `PodcastRepository` persists it (`JsonPodcastStore`), fetches feeds (`HttpFeedFetcher`), and has `EpisodeDownloader` keep only `upNext(3)` on the device, so played episodes are never downloaded. | Mixed channels (#2): assign shows to song channel IDs |
| `feedback` | Songs only (#13). `FeedbackDatabase` (`feedback.db`, the only Android code here) holds tables keyed on content hash (`ContentHash`, SHA-256 of the bytes, so the key survives moves, renames and rescans but not tag edits), plus `channel_airings` for `playback`. `feedback`: `FeedbackRecorder` appends a `FeedbackEvent` (hash, thumb, time, UTC offset, channel ID) per press; triggers abort any UPDATE or DELETE, so it stays append-only; the old tab-separated `feedback.log` (`LegacyTsvLog`) is imported on first open. `play_history`: one row per song, overwritten each time a song becomes current (`PlayHistory.markPlayed`, called from `RadioSessionCallback`): `last_played` (wall clock) and `listened_at` (DB v4, the `ListeningClock` reading; null for older plays). `listening_clock` (DB v4): total song listening time; `ListeningClock` runs only while a song plays (driven by `RadioSessionCallback`), so the shuffle's "time since heard" ignores time away and podcasts. `track_hashes`: URI → hash, valid while MediaStore size and mtime match, so `PlayHistory.lastPlayedMs` and `hashOf` answer from memory without reading files. `channel_airings` (DB v3): one row per song channel, what it last aired, written via `LiveRadio.record` after `markPlayed` returns the hash. | `learning` reads the log; #16 adds "Wrong channel" events |
| `learning` | Songs only (#14). `FeatureLayout`/`FeatureVector` (#12, layout v1): per content hash, 12 floats = thumbs up/down counts on the five moods, then The Shuffle, by channel ID. A derived cache, rebuilt from the feedback log (`FeatureVectors.from`); bump `FeatureLayout.VERSION` when the layout changes. `Models.kt` holds the swappable models, pure functions of a vector: `ChannelFitModel` reads the first 10 (which mood channels), `PreferenceModel` reads all 12 (how often). Today `ThumbRuleChannelFit` (on a mood if any thumbs up there, or if it ties for the song's fewest thumbs down; no feedback = all five) and `UniformPreference`. `LearningModels` enforces coverage (never zero channels) and the preference floor (0.1). `Learner` holds the vectors in memory, `place`s songs on the mood channels (songs from the generator's mood channels; The Shuffle untouched; empty moods drop off the dial) and gives the planner `preferenceWeight`. A thumbs press `add`s the event and calls `ChannelRepository.replace()`; the playing queue is left alone. | Swap models in `AppContainer` (`LearningModels`). Seasonal weighting (#15) reads the log, not the counts |
| `dial` | `Dial.stations` = song channels, then podcast-only channels that have a show on them (today just The Voice, `PodcastChannels.PODCASTS_ID`, `VOCAL_ONLY`). A channel joins the dial only once something is on it. `Dial.fallback` is the #4 hand-over target. With `playback`, the only code that sees both pipelines. `ChannelLineup` names seven channels with stable IDs: The Breeze, The Buzz, The Zone, The Breath, The Hall (mood slots: `AppContainer` gives `ChannelGenerator` `slotIds = ChannelLineup.moods` and `maxChannels = 5`, so the generated channels take these IDs in order; `Learner.place` then decides which songs each mood gets; empty slots stay off the dial), The Shuffle (all) (= "All songs", `all-songs`) and The Voice (= `podcasts`). `ChannelNames` (pure) is default + user names; `ChannelNamesRepository` holds it as a `StateFlow` and persists renames (`PrefsChannelNameStore`, the only Android code here). The dial, notification station and podcast page all show these names. | |
| `bluetooth` | Settings → Bluetooth (#35). `BluetoothSettings` holds "Resume on Bluetooth connection" (default on) as a `StateFlow`, persisted by `PrefsBluetoothSettingsStore`. `BluetoothConnectReceiver` (manifest, `ACL_CONNECTED`, so it works with the app closed) waits up to 6 s for that same device to appear as a Bluetooth audio output (so a watch never starts sound, and nothing plays on the speaker first), then via a `MediaController`: already playing → nothing; paused queue → `play()`; nothing loaded → scans/loads if needed and tunes `LastChannelStore` (written by `RadioSessionCallback.onChannelTuned` on every tune or fallback), so the usual resume rules apply. `BluetoothResume` (pure) is the decision and the masked-address match. Needs `BLUETOOTH_CONNECT` on 31+ (`BluetoothPermission`), asked for on the settings page. | |
| `diagnostics` | Developer mode and Settings → Debug (Features doc, Diagnostics). Tuning flow: knob release → `RadioViewModel.tune` → `controller.setMediaItem(ChannelRequest.mediaItem(id))` → `RadioSessionCallback.onSetMediaItems` → `StreamPlanner.plan` then `LiveRadio.tuneIn` (song channel) or `PodcastLibrary.queue` (podcast-only channel) → queue. Each queued item carries the channel ID in `MediaMetadata.extras` (`ChannelRequest.EXTRA_CHANNEL_ID`) so the UI follows service-side channel changes. Song items also carry their content URI (`ChannelRequest.EXTRA_TRACK_URI`), which is how the song page knows what a thumbs press refers to; episodes don't, so the thumbs hide for them. Thumbs state is per play (`PlayThumbs`): a press stays lit only until the next media item transition or the end of playback, and is never read back from the log, so every play (even of the same song) starts neutral. Until then the lit thumb pressed again cancels and the other thumb switches (`PlayThumbs.press`); `RadioViewModel` logs only the thumb lit when the play ends (or when the view model is cleared), so a cancelled or replaced press never reaches the log.

## Conventions

- **The product rule is the spec.** You still have control, but you shouldn't need it, and the app doesn't encourage using it in an unhealthy way; defaults should be right the first time.
  - **Song side (strict):** one knob. No skip, seek, track list, or second control. If a feature seems to need one, raise it instead of adding it. The thumbs (#13) are feedback, not control: they never skip or change the queue. The play glyph in the dial's centre only starts or resumes playback and disappears while playing; there is no pause button.
  - **Podcast page:** more control, because podcasts are curated, long-form and limited: add/remove feeds, assign shows to channels, mark episodes played/unplayed, see what's up next. Still no play, skip or seek; listening happens by tuning the dial.
- **Look:** only the colours in `ui/theme/Color.kt`. No accent hues, no dynamic colour, no album-art colour. Dark mode stays below full white. Keep `res/values/colors.xml` in step for pre-Compose surfaces.
- Keep channel and queue logic in pure Kotlin (no Android types; `Track.uri` is a `String`) and cover it with JVM tests in `app/src/test`. Android-dependent code stays thin. The same goes for `podcasts` (only `JsonPodcastStore` touches Android) and `feedback` (only `FeedbackDatabase`). `learning` has no Android code.
- Media3 unstable APIs: annotate the narrowest scope with `@OptIn(UnstableApi::class)` (or `@UnstableApi` on classes that expose them).
- One logical change per commit. Reference the issue (`#n`) a change works toward.

## Workflow

- **Work it through without stopping to ask.** Ask the user something only when the request is vague, or inconsistent with the specs in `docs/` or the current state of the code. Otherwise make the reasonable call and say what you decided in the PR description.
- **When development is done, open the PR.** Don't ask whether to open one; skip this if one is already open for the branch. Branch from `main`, one logical change per PR, referencing the issue (`#n`). Update the relevant `docs/` spec in the same PR when behaviour changes.
- **Enable auto-merge right after opening it**, merge-commit method (`PUT /repos/{owner}/{repo}/pulls/{n}/ccr/auto_merge`). GitHub has no repo-wide default for this, so every PR needs it; a PR without it sits unmerged after CI passes. The PR merges itself once the `check` job passes.
- If CI fails, fix it on the same branch; auto-merge stays armed.
